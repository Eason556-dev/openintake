# 通用摄入识别：架构审计与增量迁移计划

> 版本说明（2026-10-31）：0.7.0 已移除内置模型与自动餐食营养估算。本文涉及 AI 的内容为历史实现或计划；当前行为见 [轻量记录版本](LIGHTWEIGHT_RECORDING.md)。

审计日期：2026-10-23。基线：OpenIntake 0.6.2 / build 16。

本次交付是代码审计、核心测试与合成输入验证，以及后续实施计划；下列拟议能力尚未实现。本轮不修改 App、补充剂识别、Watch 同步或 HealthKit 写入逻辑，不创建真实摄入记录。

## 1. 结论与七个问题的回答

现有项目已有可复用的本地产品、标签证据链、确定性单位换算、摄入事件快照和 HealthKit 持久化 outbox。主要缺口在普通餐食：模型仍直接生成营养数值，合理性校验并不等于营养事实验证；不同入口的校验也不一致。应在现有基础上增量迁移，无需重写 App。

| 审计问题 | 当前实现与结论 |
| --- | --- |
| AI 如何从 OCR 或自然语言生成营养值？ | 标签路径提取原文名称、含量引文和证据 ID，再由程序读取数字、单位、基准并验证。文字餐食和照片餐食则允许模型直接输出每 100 g / mL 的营养估算，程序再按实际份量计算。两者不能视为同等可信的数据来源。 |
| 是否直接猜测所有营养素？ | 没有要求填满所有营养素；提示词要求未知省略，并建议少量常见指标。但餐食模型可选择除饮水外的 38 种营养类型并直接生成数值，没有参考数据依据的强制约束。因此存在无来源数值推断，并非“必须猜全 39 项”。 |
| 验证器能否识别不合理的宏量营养素？ | 能检查有限正数、单位维度、重复类型、单项上限与宏量总质量。不能完整检查糖/碳水包含关系、脂肪子类关系、能量一致性。手动食品、餐食、普通 Product 三条路径的规则不同。 |
| 标签与餐食是否错误共用一种策略？ | 没有完全混用：标签有独立提取、原文证据验证和规则回退；文字与照片也分别实现。问题是餐食内部尚未区分普通食材、自制菜、餐厅菜等来源策略；仍以模型数值估算为主。 |
| 已保存产品能否重复使用？ | 可以。产品库可通过 App、快捷操作及 Watch 快速记录，摄入事件冻结产品版本。但一次餐食通过 `logMeal` 记录后，不会自动成为可复用产品；没有完整配方库或产品修改历史。 |
| HealthKit 不支持的成分如何保留？ | `Ingredient` 保存原名、含量、单位、证据、化学形式及关系。精确映射、需同意的宽泛映射、本地保留分别处理；当量和不支持的单位不强行写入。该机制主要覆盖补充剂，尚非所有食品通用模型。 |
| AI 不可用时还能做什么？ | 饮水、手动食品/饮料营养录入、保存产品复用、标签规则解析、文字餐食名称与明确质量/体积提取、已有记录同步和撤销仍可用。普通食材尚无离线参考库；规则回退不会补出未知营养。当前全无营养值的餐食不能提交为摄入事件，需补充已知值。 |

## 2. 当前处理链与代码证据

### 标签与补充剂

`App/Scanner.swift` → `App/DocumentOCR.swift` → `Sources/IntakeCore/LabelRecognitionSession.swift` → `App/OptionalAI.swift` → `Sources/IntakeCore/SemanticValidation.swift` → `Sources/IntakeCore/Ingredients.swift`。

- 可用时采用 `RecognizeDocumentsRequest`，保留文字、位置、页码、表格行列、候选文本和置信度；旧路径使用 Vision 文本识别。能力受系统和设备限制，不能宣称所有语言均支持。
- `AppleSemanticProvider` 要求模型返回原文引文、证据 ID 和关系；数值由 `LabelEvidence` 从引文提取。分批解析，限制输入规模。
- 产品表头、计量基准和推荐用量仍依赖离线表头解析，并非所有字段都由模型语义理解。
- `LabelRecognitionSession` 使用 generation 防止过期异步响应覆盖新草稿，协调规则结果与 AI 结果。
- `SemanticValidator` 保守验证成分关系。目前显式允许的关系集中于 fishOil → omega3 → EPA/DHA、turmericExtract → dryHerbEquivalent。其他合理关系也可能进入待确认状态；这还不是通用包含关系系统。
- `HealthPlan` 抑制同类型父子重复累计、阻止冲突映射；当量不作为实际剂量。Omega-3 的宽泛映射需明确同意。总脂肪与其子类是不同指标，不能简单相加为一个“脂肪总量”。
- IU 仅有特定营养素规则，例如维生素 D；DFE、RAE、其他无法可靠转换的单位保留本地，不套通用公式。

### 文字与照片餐食

`App/TextMealRecognition.swift` → `Sources/IntakeCore/TextMeal.swift`；`App/MealRecognition.swift` → `Sources/IntakeCore/DailyIntake.swift`；共同进入 `App/MealEditor.swift` / `Sources/IntakeCore/MealReview.swift`。

- 文字模型同时提取食物、引文、实际数量及每 100 单位营养估算。引用能证明用户说过什么，不能证明营养估算准确。
- 文字解析按原文检查名称、质量/体积和遗漏段落；缺失项目回退为未知营养条目。mL 有独立路径，不自动转为 g。
- 照片模型返回每 100 g 估算，不负责实际食用重量。现有 UI 在已有文字或条目时不允许照片分析覆盖它们，应保留这一保护。
- 照片解析最多处理前 20 项；整项宏量检查不通过时不加入结果，缺少对应条目的明确错误说明。这是静态代码发现，未在本轮调用模型复现。
- 模型输出缺少参考资料 ID、数据版本、逐数值估算区间和方法记录；`aiEstimate` 与自由文本说明不足以形成可复算的来源链。
- 部分模型字段要求中文说明，内部 ID 已相对独立，但展示语言与解析输出尚未彻底解耦。

### 产品、事件与 HealthKit

`Sources/IntakeCore/Models.swift`、`ManualNutrition.swift`、`App/IntakeStore.swift`、`App/HealthWriter.swift`。

- 扫描/保存产品不生成摄入事件。`logMeal` / `log` 才生成事件，先持久化，再同步。
- `Product.revision` 标识版本；`IntakeEvent` 冻结产品和 `healthWriteSnapshot`，保护历史计算和重试。
- 产品编辑会替换产品库中的当前版本；曾用于事件的快照仍存在，但未使用过的旧产品版本没有完整历史档案。
- 写入适配器逐类型检查权限，保存后验证样本；失败保留事件并重试。撤销/恢复与样本标识、同步版本相连。Watch 请求 ID 用于防重，不能在本次模型迁移中破坏。
- 保存成功证明样本进入 HealthKit，不证明营养数值真实；数值可信性必须在生成事件之前解决。
- 同一请求重试与真正重复用餐是不同问题。已有事件/请求防重不等于对不同草稿中相同食物做了通用语义去重。

## 3. 已验证的缺口

以下使用合成输入直接调用当前核心代码，不是对具体食品营养的判断，也没有写入 HealthKit。

| 探针 | 实际结果 | 含义 |
| --- | --- | --- |
| 每 100 g：糖 20 g、碳水 10 g | `MealValidation.validate` 接受 | 餐食路径缺少包含关系检查；手动食品已有相关检查，规则不一致。 |
| 每 100 g：能量 10 kcal、脂肪 20 g | 接受 | 缺少能量合理性检查。未来检查应允许纤维、酒精、标签取整等差异，不能以严格 4/4/9 等式代替完整规则。 |
| 明确手动填写糖 0 g | 餐食路径拒绝 | 已知零与未知缺失没有在各入口一致处理。必须保留可靠的已知零，同时禁止未知填零。 |
| `.database` 来源的已知营养值 | 餐食路径拒绝 | 接入离线参考库之前必须调整来源验证策略，而非将数据库值伪装成 AI 或手动值。 |
| 普通 Product：标注每 100 g、蛋白质 150 g | `Product.validate` 接受 | 旧营养数组路径缺少同等合理性校验；这是核心入口漏洞，并非断言现有某个 UI 已产生该数据。 |
| 两项各 100 g，一项糖 10 g，另一项糖未知 | 合计糖 10 g | 没有把未知填成数组中的零，但缺少逐营养素 completeness。仅通用文字说明“未知未纳入”，不能把已知小计当完整总量。 |
| 饮料每 100 mL 糖 10 g，实际 250 mL | 合计糖 25 g | 已有确定性体积缩放正确，应保留。 |

此外：餐食质量上限规则同样应用到每 100 mL，不能在未知密度时把体积等同质量；手动饮料路径又采用不同限制。应将“绝对结构错误”“基于已知基准的关系错误”“需要复核的合理性警告”分开。

P0 风险集中在无参考依据的餐食估算、入口间校验不一致、部分已知数据的表达和静默丢项。当前证据不支持宣称“全部 HealthKit 写入错误”，也不能因 165 项测试通过就断言没有这些缺口。

## 4. 模型迁移：增量扩展，不重写历史

建议保持 Product 定义、RecognitionDraft 草稿、IntakeEvent 实际摄入三个边界。Product 是实体，不应与 Food/Beverage 作为同层互斥类别；类别可扩为 food、beverage、supplement、medication、water，包装食品/自制/餐厅则是独立场景属性。

| 模型部分 | 已有 | 增量设计 |
| --- | --- | --- |
| 产品身份 | ID、名称、revision | 品牌、口味、地区、包装规格、可选条码、类型与场景；同条码也不能覆盖不同地区/配方版本。 |
| 计量基准 | 每份、每粒、每 100 g/mL、实际质量/体积 | 结构化份量、计数单位、生/熟状态、可食部；密度和烹调产率只有带来源时才允许换算。 |
| 原始资料 | OCR 文本/结构/证据、部分 AI 原始响应 | 持久化图片引用、文档版本、完整输入引用；图片是可选本地附件，不进入公开仓库。 |
| 营养事实 | 标准 ID、值、单位、origin | 已知值（允许可靠零）或未知及原因、来源引用、方法/版本、估算区间、确认状态。缺字段不能默认零。 |
| 成分关系 | parentID、component/equivalent、化学形式 | 区分组成、包含、等效、别名、化学形式；只对同基准且互斥的子项做质量相加。 |
| 聚合结果 | 已知数值求和 | 每营养素的 knownSubtotal、complete/partial/unknown、参与项和缺失项；区间只在有依据时传播。 |
| 修改历史 | 当前 revision 与事件快照 | 新增只追加的产品版本与修改原因；用户修正不覆盖原始证据。 |
| 实际事件 | 冻结产品、份数、时间、写入计划、同步状态 | 引用新增版本/来源信息；继续冻结写入计划，保持事件 ID 和重试幂等。 |

迁移原则：新增字段可选、旧文件可读取；旧来源无法还原则标记 legacy/unknown，不补造来源。以真实旧结构的匿名合成夹具验证解码。不得重新估算历史事件或自动重写已同步样本；用户明确更正后才通过既有撤销/更正流程处理。数据升级失败应保留原文件，不能用空库覆盖。

## 5. 多策略管道

统一的是输入、事实、验证报告和写入计划接口，不是一个覆盖所有场景的巨型 Prompt。

| 场景 | 建议策略 | 信息不足时 |
| --- | --- | --- |
| 包装食品/饮料 | OCR → 识别列和基准 → 提取标示值 → 确定性换算 → 预览确认 | 保留未读字段；多列/多规格需要选择，不拼接成一份。条码仅查本地产品，不是营养来源。 |
| 普通食材 | 识别身份及生熟状态 → 匹配小型离线参考条目 → 实际可食重量缩放 | 显示候选或手填；无匹配不生成营养事实。 |
| 自制餐食 | 用户提供食材/配方 → 分项匹配 → 确认用量和产率 → 计算整锅及食用份量 | 不从菜名猜油盐；成品菜与其食材不能重复计入。 |
| 餐厅食品 | 有版本/地区的可靠营养资料优先 → 否则使用可解释的参考或配方估算 | 餐厅名/菜名本身不是证据；来源不明保持未知或明确待核实，不给虚假精度。 |
| 营养补充剂 | 保留现有原文提取与证据验证 → 关系/单位 → 每粒及实际粒数 → 映射 | 无法确认的关系和特殊单位留本地，继续用户核对。 |
| 药品 | 独立类型及本地资料边界，单独评估药物 API | 任何剂量都不进入营养映射；不能把“模型说不是药”作为唯一安全边界。 |

AI Provider 只提出身份、结构、候选匹配与证据；计算层独立于模型。现有标签 Provider 接口可参考复用，但不要求把正常标签流水线替换成新框架。图片不覆盖明确文字和已确认重量，骨头/包装/容器重量不作为已确认可食重量。

## 6. 本地数据与来源策略

- 本地产品档案作为首选，明确选择版本后快速复用。
- 小型通用食物参考数据先审查许可证、版本和地区适用性；随包或用户可选导入，保留来源及条目 ID。当前尚未选定或集成任何食品数据集。
- 不要求服务器、付费 API、账号或自建模型；AI 不可用时手动与已保存资料仍完整可用。
- 导入/导出应版本化并先验证再原子合并；预览重复和版本冲突。导入产品不创建摄入事件，导入历史不默认重新上传 HealthKit。
- 产品版本引用不可变；图片、原始文本和历史导出均属用户私有资料，不成为测试样本或提交文件。
- 全部营养未知的食品可以作为本地条目保存，清楚标注无可同步营养；不以“同步成功”掩盖没有写入。

## 7. 实施顺序及每阶段验收

### P0：堵住现有可信性和校验缺口

1. 在 IntakeCore 中形成共享的基准/单位/关系验证报告，逐个接入餐食、手动食品与旧 Product 路径。报告区分阻断错误与需要解释的警告，不能只返回泛化“无效”。
2. 加入糖/碳水、脂肪子类、基于有效基准的质量关系及能量一致性检查。考虑各地区碳水定义、取整容差；能量异常优先要求复核，不自动改值。缺失脂肪总量不阻止已有子类，也不生成总量。
3. 分离模型识别与数值来源。当前模型自由生成数值迁移为“未核实建议”，不能只因落在范围内就变成获准写入事实；产品标签、手动明确输入和有版本的参考计算仍可记录。用户保留最终确认权，但点击确认不能凭空增加来源可靠性。
4. 引入逐营养素完整度。保留已知贡献，不要求每个营养素都有值；部分已知时展示“已知部分”，确认页明确其写入范围。HealthKit 标量记录只代表已确认的已知贡献，不宣称整餐完整。未知项和范围继续留本地，不能写成零或另造营养类型。
5. 照片结果过滤/截断改为显式待复核，保留食物条目；文字来源优先、generation 防护和确认状态不退化。
6. 迁移当前估算来源时不改写历史事件；新增来源标记与证据字段，旧数据明确标识历史估算。

验收：把第 3 节的缺口转为回归测试；包含有限值、已知零/未知、不同入口一致性、部分值、饮料缩放、AI 不可用、确认开关、重复请求、失败重试、撤销恢复。运行完整 `swift test` 和涉及的 iOS/watchOS unsigned build；在真机检查预览、授权与真实样本值。此阶段不以新增识别品类为目标。

### P1：包装食品与补充剂标签

- 复用现有 OCR 和补充剂流水线，为普通食品增加明确的标签策略和多列基准处理。
- 校验每份/每包装/每 100 单位、地区差异、盐与钠的显式换算依据、多语言别名及化学形式。
- 扩展成分关系规则的表达能力，保留对未知关系的人工确认；不能用某品牌固定数值替代通用解析。

验收：同品牌不同口味/容量、英法双语、跨行名称与数值、标签缺漏、IU/DFE/RAE、鱼油层级、植物当量、无法映射成分。既有维生素 C 和 Jamieson 回归必须全部保留；真机扫描验证另记，不以模拟输出代替。

### P2：离线参考食材与复合餐食

- 先接入小型、许可清楚、版本固定的参考条目；数值计算与 AI 完全分离。
- 覆盖米饭、肉、蔬菜、水果的生熟匹配；自制菜按互斥食材、整锅/份量和有依据的产率计算。
- 汤、饮料按体积基准或明确密度换算，禁止 mL 默认等于 g；餐厅无可靠资料时不强制产生结果。

验收：离线及 AI 关闭状态完成匹配/手动选择/计算；验证来源版本、未知传播、重复成品与食材、单位与产率、实际可食量、复合部分未知及结果可复算。完整构建和 HealthKit outbox 回归独立通过。

### P3：复用、历史与交互

- 完善产品身份、版本历史、常用餐食/配方复用、本地导入导出及冲突预览。
- 预览区分标签、参考估算、AI 未核实建议、手动、未知；解析语言、内部 ID、界面语言分离。
- 扩展快捷指令、Widget、Watch 时继续使用同一事件与 outbox；Watch 只快速使用已配置资料，不建立第二个独立写入通道。

## 9. Apple API 核对

- 安装的 iPhoneOS SDK `HKTypeIdentifiers.h` 列出 39 个 Dietary quantity identifiers。对应单位和运行时可用性仍由现有 catalog/适配器检查，不能因此承诺所有 HealthKit 类型都可写。
- `HKMedicationDoseEvent` 在当前 SDK 的属性只读且 `init` 不可用，当前检查没有发现公开剂量事件创建接口；不能承诺 OpenIntake 写入 Apple 药物服用记录。药物应继续独立，未来接入须再次核查目标 SDK。
- Apple 的同步标识与版本接口支持样本更新的幂等机制；仍须保留应用持久化事件和保存后验证，不能只依赖授权回调。

官方参考：[Nutrition Type Identifiers](https://developer.apple.com/documentation/healthkit/nutrition-type-identifiers)、[HKMedicationDoseEvent](https://developer.apple.com/documentation/healthkit/hkmedicationdoseevent)、[HKMetadataKeySyncIdentifier](https://developer.apple.com/documentation/healthkit/hkmetadatakeysyncidentifier)。本轮网页正文获取受文档渲染限制，类型数量与药物构造限制以本机 SDK 头文件复核为依据。
